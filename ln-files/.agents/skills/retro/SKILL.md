# Retro

指定された会話・作業を振り返り、今後の判断を改善する環境の変更を提案する。調査だけの依頼では変更せず、既に許可された改訂はその範囲で進める。

## 情報の確認

- `writing-for-agents` を読み、対象の会話・作業の一次資料を確認する。指定がなければ現在の会話を対象とする。
- 長期間の調査では、対象期間、会話の続き、重複、確認できなかった資料を整理する。「全件」の依頼はキーワード検索や要約だけで確認済みとしない。
- その時点の要件・権限・利用可能な情報で判断を評価する。後から変わった要件や、通常の好みの探索を失敗として扱わない。
- 現在のコード・指示・ツールも確認し、既に解消した問題を未解決として提案しない。

## 改善先の選択

繰り返し、影響、ユーザーの介入、調査・実行コストを見て、重要な候補から示す。

| 問題 | 改善先 |
|---|---|
| 必要な情報を見つけられない | 既存文書への参照、情報へのアクセス、ツールの表示 |
| 同じ機械的な失敗を繰り返す | 案件側の既存検査・正式ツールの修正候補 |
| 原因調査、案の選定、検証範囲の判断が弱い | 関連スキルの判断基準 |
| 許可・禁止・確認条件が曖昧 | AGENTS.mdの該当規則 |
| 工程や出力が増えても効果がない | 不要な規則・作業・参照の削減 |

案件固有の失敗は、その適用範囲を保って提案する。検査がないことだけで問題と断定せず、既存の実行方法を確認する。CIの追加・実行などは効果、費用、権限に照らして判断し、振り返りのために自動で起動しない。

レビューに必要な周辺コードや要件は確認する。レビュー担当が常に差分だけで判断できるとはみなさず、このスキル自体は追加の担当者やレビュー工程を必須にしない。

## 提案と効果の確認

各提案を、観測された問題、直す場所、期待する判断の変化、変更の費用と対応させる。成功例と維持すべき制約も残す。単発の事例から万能な規則を作らない。

ハーネスの改訂や改訂前後の比較を行う場合は、[低コストでの評価](references/evaluation.md)を読む。形式の検査結果と、実作業で効果を確認できたかを区別して報告する。
