# 低コストでの評価

指示の改訂は改善の仮説として扱う。形式・参照の整合性、判断事例での確認、実作業での結果を区別する。

## 通常は実作業を使う

同じ作業を評価のためだけに再実行せず、既存の成果物・検証・会話から、狙った判断が行われたかを確認する。

- 原因の説明に証拠があり、未確認事項を仮説として扱ったか。
- 既存手段を調べ、追加した機能・抽象化に現在の必要性があるか。
- 検証結果の範囲を超えて完了を報告していないか。
- 不要な確認が減ったか。要件変更・権限など必要な確認は維持されたか。

ユーザーから修正指示がなかったことだけで成功としない。結果の根拠と、判断を修正した介入の内容を見る。記録は既存の報告やretroに短く含め、毎回の採点表・別ファイルを要求しない。

## 比較が必要な場合だけ小さく試す

挙動を大きく変える改訂など、通常の確認では判断できない場合に使う。

1. 過去の実例から、改訂の目的に関係する少数の場面を選ぶ。まず1件、増やしても3件程度とし、結論が出た後の会話を入力に混ぜない。
2. 同じ要件と必要な資料で、改訂前後の「選ぶ方針・根拠・次に確かめる点」だけを比較する。最初から全実装・全会話を再生成しない。追加のモデル実行には、利用可能な権限と費用の制約を適用する。
3. 評価条件を先に決める。文章量、規則への言及、原因・案の数を品質の代わりにしない。効果が不明なら不明として止め、試行や規則を増やし続けない。

条件の例：

| 場面 | 確認する判断 |
|---|---|
| 複数の処理にまたがる障害 | 呼び出し経路から原因を絞り、無条件の再試行や防御の追加を先に選ばない |
| 既存ライブラリで対応できる連携 | 実環境と終了・キャンセルの契約を確認し、独自実装の必要性を判断する |
| 原因が明確な局所修正 | 必要な修正・検証で終わり、設定・汎用基盤・長い承認工程を増やさない |

特定のライブラリ名や「自作しない」という結論への一致を合格条件にしない。判断だけの比較は、実装や実環境での効果の証明にはならない。

## 定性的な成果

見た目や文章などは、目的と読み手を揃え、必要な場合だけ少数案を匿名で比較する。「意味が伝わる」「目的の情報を見つけられる」など具体的な観点を使う。新旧の名前を隠せても、入力条件と制約は隠さない。

同じAIによる自己採点や、変更後への好みだけで品質向上と断定しない。分かる範囲を報告し、評価のための大量生成、全履歴の再読、常設のCIを追加しない。
