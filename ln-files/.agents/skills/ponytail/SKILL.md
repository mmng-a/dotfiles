# Ponytail

必要な動作を保ち、将来の理解・変更・運用を難しくする余分な実装を抑える。行数、ファイル数、説明の短さを目的にしない。現在の作業に適用し、別の依頼へ無条件に持ち越さない。

## 追加する前に確かめる

- この機能・設定・抽象化は、現在の要件や確認された問題に必要か。
- 既存コード、標準機能、プラットフォーム、導入済みの依存関係で満たせるか。
- 独自実装より、保守されているライブラリの利用が妥当か。選定が必要なら `software-design` を使う。
- 層を1つ取り除くと、必要な責任が失われるか、単なる転送がなくなるだけか。
- 共通化によって知識・変更箇所がまとまるか、無関係な処理の結合が増えるか。

小さな重複だけを理由に共通基盤を作らない。必要性のある既存の抽象化も、実装が1つという理由だけでは取り除かない。

## 判断と変更

- 将来の利用を想定した拡張点、使われない設定、重複した状態管理は、今必要な責任を確認してから省く。
- 追加する複雑性には、満たす要件または解消する具体的な問題を対応させる。理由を説明できなければ、より単純な構成を選ぶ。
- 読みやすく責任が明確になるなら、適切な関数分割、名前、型、コメントを保つ。式の短縮やファイルの統合を優先しない。
- 要件の削減や既存動作の廃止が必要なら、理由と影響を伝えて確認する。明示された機能を省いた版を先に実装しない。
- セキュリティ、データ保全、入力検証、エラー処理、アクセシビリティ、互換性、必要なテストを簡素化のために落とさない。検証は既存の方法を使い、実装の分岐数だけで新しい自己検査を加えない。
- 依頼外の削除やリファクタは提案にとどめる。意図的な制約を残す場合は、保守に必要な理由・限界・見直す条件を既存の記法で記録する。

重要な判断と影響が伝わる長さで説明し、必要な検証と報告を終える。過剰設計が見つからなければ、そのためだけに差分を作らない。
