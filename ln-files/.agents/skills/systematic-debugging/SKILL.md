# Systematic Debugging

症状を説明できる証拠を集め、原因に対応する修正を選ぶ。調査のみの依頼では変更しない。工程の詳細さは変更規模と不確実性に合わせる。

## 症状と証拠

- 期待する動作、実際の動作、対象の版・環境・入力を確認する。ユーザーの原因推測と観測事実を区別する。
- 既存のテスト・ログ・設定・直近の差分と正常例を調べる。実際の呼び出し経路とデータの流れを追い、期待から外れる箇所を絞る。
- 再現できる場合は、元の症状を検出する小さな再現方法を確保する。自動テストが適切なら既存の方法を使い、可能なら修正前の失敗を確認する。
- 再現できなくても証拠に基づく調査を続ける。未確認の経路・条件と仮説を明示し、再現不能を原因確定や調査終了の理由にしない。
- 複数の処理にまたがる場合は、関連する入出力、設定の伝播、状態の所有者を確認する。追加の計測は疑わしい箇所へ絞り、機密情報、実環境の負荷、変更権限に配慮する。

原因が明確な局所修正では、該当箇所と影響する利用箇所を確認し、修正・検証へ進む。

## 原因の説明

有力な仮説を、他の説明と区別できる観測・実験で確かめる。推測上の修正を積み重ねず、何を確かめたかと結果を対応させる。

- **直接的な原因**：どの入力・状態・処理が、どのように症状を発生させたか。
- **発生を許した要因**：仕様の不足、責任の配置、状態管理、依存先との契約など、同じ種類の不具合を生む仕組み。
- **見逃した要因**：元の症状や対象環境を既存の検証で検出できなかった理由。

証拠がなければ上位の原因を作り出さず、未確定の説明は仮説として扱う。性能問題では測定区間・分母・負荷・キャッシュなどの条件を揃え、時間の内訳を調べてから主因を判断する。

修正が説明どおりに効かない場合は、仮説、再現方法、共有状態や責任の配置を見直す。試行回数だけで設計欠陥と断定しない。設計の選択が必要なら `software-design` を使い、要件・範囲・権限の変更が必要な場合に確認する。

## 修正の選択

- 有力な案が複数ある場合は、再発防止、変更範囲、互換性、複雑性、運用への影響を比べ、選定理由を短く示す。自明な案に比較表を作る必要はない。
- 共通処理で直す場合は、関連する呼び出し元にも同じ契約が適用できるか確認する。報告された1経路だけ直すことも、全経路へ一律の防御を加えることも、調査なしに選ばない。
- 依頼された範囲で原因に対応する変更を行う。修正に必要な変更と、別途の改善案を分ける。

## 検証と終了

元の症状の解消と、変更が影響する既存利用を確認する。可能なら同じ再現方法で修正前後の失敗・成功を比較する。他者の変更を戻して比較せず、必要なら隔離した環境を使う。

単体テスト・モックで確認した契約と、実際の実行環境・成果物・稼働状態で確認した事実を区別する。検証が未完了なら理由と残る不確実性を報告する。有効な既存の検証結果は再利用し、一時的な調査用変更を片付けて終了する。
