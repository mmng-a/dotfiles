# Software Design

目的を満たし、理解・変更・運用しやすい設計を選ぶ。通常の技術判断は自律的に進め、要件・作業範囲・権限が変わる場合に確認する。毎回の設計承認や設計書の作成を必須にしない。

## 目的と既存の手段

- 求める結果、合意済みの制約、対象環境、既存仕様、完了条件を把握する。ユーザーの実装案と必要な結果を区別する。
- 関連する既存コード・設定・依存関係を先に調べる。標準機能、プラットフォームの機能、既存ライブラリの適合性を確認し、必要なら外部の候補を調べる。
- 候補の重要な仕様は公式文書・実装など一次資料で確認する。利用できない情報源は調査済みとして扱わない。
- 適合する手段が見つかれば調査を終える。検索先や候補を網羅しない。候補の検証に導入が必要なら許可された隔離環境で試し、採用を決める前に本体の依存関係を増やさない。プラグインの追加は利用規則に従う。

## 案の選択

既存の手段をそのまま使う、必要部分を接続する、自作する選択肢を実際の要件で判断する。複数の案が有力なら、判断を左右する差を比較する。

- 必要な動作、実行環境、既存構成との適合性。
- 保守状況、ライセンス、セキュリティ、更新・配布・運用の負担。
- 独自実装として引き受ける責任と、導入によって減らせる責任。
- 信頼性、性能、調査・検証のしやすさ。

既存ライブラリの採用も、数行の自作も自動的な正解にはしない。自作する場合は、既存手段で満たせない理由と保守する範囲を明確にする。現在の要件に不要な拡張点や汎用化は加えない。

選定を左右する不確実性があれば、その点だけを実際の環境やAPIで小さく試す。試作を新たな製品機能として残さない。性能・品質を理由に置き換える場合は、既存方式と条件を揃えて効果を確かめる。

## 責任と契約

呼び出し側が知る必要のある情報を少なくし、変更・障害への対応を適切な箇所へ集める。層やファイルの数、特定の用語を設計の良さの基準にしない。

対象の設計に関係するものを確認する。

- 入出力、不変条件、処理順序、エラーの意味。
- 状態と外部資源の所有者、作成から終了・解放までの責任。
- 非同期処理の完了、並行実行、キャンセル、失敗時の後始末。
- 呼び出し側が依存する設定、環境、性能上の前提。

ラッパーや新しい境界は、業務上の変換、資源管理、複数の利用箇所に散る複雑性の集約など、具体的な責任がある場合に置く。単なる転送や将来の差し替えだけを理由に層を増やさない。現在必要な安全性・互換性・理解しやすさを行数削減のために落とさない。

## 実装と終了

選んだ案と重要なトレードオフを短く伝え、許可された範囲で実装・検証する。呼び出し側と同じ入口から主要な動作を確かめ、モックと実環境で確認した範囲を区別する。

完了条件を満たした時点で終了する。別途の調査資料や設計書は、依頼または継続的な保守に必要な場合にだけ残す。
